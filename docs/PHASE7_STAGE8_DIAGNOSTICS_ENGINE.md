# SAYRA Enterprise Windows Client
# Phase 7 — Stage 8: Enterprise Recovery Diagnostics Engine Documentation

## 1. Overview & Architecture

The **Enterprise Recovery Diagnostics Engine** is a dedicated diagnostic observation subsystem designed to collect, aggregate, analyze, and persist diagnostic data generated by across all Phase 7 resilience components.

Adhering strictly to **Clean Architecture** and **SOLID** principles:
- **Separation of Concerns:** This stage only generates and preserves diagnostics. It does not perform any recovery, self-healing, resource modification, or security validation actions.
- **Dependency Inversion:** High-level diagnostic logic interacts strictly through clean, fully documented asynchronous interfaces (`IRecoveryDiagnosticsEngine`).
- **Open-Closed Principle:** The export system utilizes pluggable and fully extensible exporters (`IDiagnosticsExporter`) to support outputting reports to new formats (e.g. ZIP, HTML, PDF) without modifying the core `RecoveryDiagnosticsEngine` class.

```
       [ IHealthMonitor ]     [ IResourceMonitor ]     [ ISecurityHardeningService ]
               \                       |                      /
                \                      |                     /
             +-------------------------------------------------+
             |            RecoveryDiagnosticsEngine            |
             +-------------------------------------------------+
             /         |                       |               \
            /          |                       |                \
   [ IDiagnosticsExporter ]  [ DiagnosticsRecommendationEngine ] [ IEventDispatcher ]
      /               \
[ TXT Exporter ]  [ JSON Exporter ]
```

## 2. Report Generation Workflow

The diagnostics engine aggregates state from five core components:
1. **Health Monitor (`IHealthMonitor`):** Provides detailed subsystem states, scores, heartbeats, dependencies, and transition history.
2. **Self-Healing Engine (`RecoveryMetricsCollector`):** Provides total attempts, success rate, failed recoveries, duration, and active interlocks.
3. **Crash Recovery Manager (`ICrashRecoveryManager`):** Provides startup timestamps, recovery summaries, and previous dirty shutdown reasons.
4. **Resource Monitor (`IResourceMonitor`):** Provides CPU, Process & System RAM, Free Storage, Handle, Thread, GDI counts, GPU usage, and pressure level evaluation.
5. **Security Hardening (`ISecurityHardeningService`):** Provides validation results of Configuration, Policies, Database, Media, Plugins, Packages, and Executables.

---

## 3. The 6 Core Report Types

### 3.1 Startup Report
Focuses on boot checks and environment evaluation:
- Startup timestamp and duration.
- Flag indicating whether a crash/abnormal recovery was executed.
- List of components recovered and any registered warnings/errors during boot.

### 3.2 Health Report
Details the state of all tracked subsystems:
- Detailed state (Healthy, Warning, Critical, Offline) and health score.
- Last heartbeat timestamp and dependencies list.
- Last 5 transition history messages.

### 3.3 Recovery Report
Aggregates self-healing outcomes:
- Total self-healing attempts and success rate (%).
- Average duration of successful recoveries.
- Active interlocks and escalated incident counts.

### 3.4 Failure Report
Compiles active failures and exceptions:
- Detailed exceptions and subsystem stack traces.
- Rule-based suggestions formulated specifically from active subsystem failures.

### 3.5 Resource Report
Provides high-fidelity performance metrics:
- CPU and GPU usage percentages.
- Process working set and system available memory.
- Thread, handle, and GDI handle counts.
- Disk and Network IO transfer rates, and hardware temperature.

### 3.6 Security Report
Summarizes cryptographic authenticity validations:
- Results of JSON config, SQLite DB, local policies, ad media, plugins, updates, and Authenticode signatures.
- List of detected critical violations and active tampering alerts.

## 4. Diagnostics Metadata

Every generated report, whether human-readable plain text or JSON, contains standardized auditing metadata:
- **Timestamp:** Exact UTC timestamp of generation.
- **Machine ID:** Workstation machine name.
- **Application Version:** Client software version (configured via options).
- **Build Number:** Build tag or identifier.
- **OS Version:** Workstation Operating System version.
- **CorrelationId:** Unique Guid tracing the generation pass.
- **Generated By:** Subsystem identity.
- **Report Version:** Format schema version.

## 5. Extensible Export Pipeline

Pluggable exporters implement the `IDiagnosticsExporter` interface:
```csharp
public interface IDiagnosticsExporter
{
    string Format { get; }
    Task<string> ExportAsync(ReportType reportType, string content, string destinationPath, CancellationToken cancellationToken);
}
```
- **PlainTextDiagnosticsExporter (`TXT`):** Outputs beautifully aligned text reports with a standardized header.
- **JsonDiagnosticsExporter (`JSON`):** Outputs structured JSON envelopes containing root-level metadata and report-specific payloads.
- **Future Extensibility:** Supporting additional formats (like `ZIP`, `HTML`, `PDF`) simply requires writing a new class implementing `IDiagnosticsExporter` and registering it in DI. No changes are required in `RecoveryDiagnosticsEngine`.

---

## 6. Rule-Based Recommendation Engine

Actionable, deterministic recommendations are generated strictly from live telemetry evidence using a rule-based engine:
- **High Memory Usage:** Suggests cache cleanups and process evictions if available RAM is low or process memory exceeds warning ceilings.
- **Repeated Subsystem Failures:** Triggers suggestions to inspect SQLite logs and run manual validation checks if any subsystem undergoes multiple failure transitions.
- **Recovery Loops:** Detects if a subsystem's automatic healing has been throttled to prevent CPU/RAM resource storms.
- **Configuration/Policy Tampering:** Advises operators to re-fetch cryptographically signed JSON profiles from the server on signature mismatch.
- **Database Corruption:** Guides operators on re-indexing or forcing a secure database recreation on SQLCipher integrity failures.
- **Network Instability:** Recommends checking ethernet links and socket pinning certificates on offline network states.

---

## 7. Persistence & Retention Policy

Generated reports are persisted locally to a configurable reports directory.
- **Pruning / Retention limit:** Configured via `RecoveryDiagnosticsOptions.RetentionLimit` (default is 50 files).
- **Thread-Safety:** Pruning is executed thread-safely using a dedicated sync-lock on a background thread during file persistence. The oldest files (based on modification timestamp) are safely deleted once the limit is exceeded.
- **Safe Overwrite:** Custom export paths support safe overwrite. Standard reports are versioned using timestamps and CorrelationIds.

---

## 8. Extension Points

1. **New Exporter:** Write a class implementing `IDiagnosticsExporter` and register it in the dependency container:
   ```csharp
   services.AddSingleton<IDiagnosticsExporter, MyPdfExporter>();
   ```
2. **Additional Rules:** Update `DiagnosticsRecommendationEngine.EvaluateRules()` to append new rules without modifying generation pipelines.
3. **DI Configuration:** Modify standard limits via `appsettings.json` under `"Recovery:Diagnostics"` section (e.g. `ReportsDirectory`, `RetentionLimit`, `EnableJson`, etc.).
